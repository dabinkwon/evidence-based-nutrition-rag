# 중요한 결정

## D008 — PDF 활용 보류 및 최신 공식 웹 자료 추가

- 날짜·상태: 2026-10-21 / 확정(사용자 PDF 제거·최신 정보 추가 요청).
- 문제: PDF 이용 조건·정오표 검토가 남아 있으며 사용자가 다른 최신 정보 활용을 요청했다.
- 대안: PDF 수집 계속 / 프로젝트 PDF 제거 후 이용 조건이 확인된 웹 텍스트 보충. 후자를 선택했다.
- 선택·이유: 2025 농촌진흥청 식생활 실천 점검자료와 2026 식약처 영양정보 정책 추가, 출처·게시일·이용 조건·수집 경로 확인. 기존 웹 자료는 삭제하지 않는다.
- 제약·단점: 최신 기사라고 최신 영양 기준은 아니다. 정책 기사는 `policy_background_only`로 구분하며 개인별 권고에 사용하지 않는다.
- 검증 근거: W012, `data/guidelines/manifest.json`, `chunks.jsonl`. PDF 삭제 전 6개 메뉴 감사 기록은 유지하되 로컬 재검증 불가 표시.
- 재검토 조건: 최신 공식 웹 영양 기준 확보, 원문 수정·이용 조건 변경·PDF 재사용에 대한 사용자 방향 변경 시.
- 관련: D006의 PDF 원문 확보 작업은 보류, D007의 웹 근거 체계 유지.

## D007 — 이용 조건이 명확한 공식 웹 텍스트로 설명 근거 초기 확보

- 날짜·상태: 2026-10-21 / 확정(사용자 근거 확보 요청에 따른 LLM 수집 선택).
- 문제: 메뉴 데이터만으로 음식 선택의 일반 원칙을 설명할 수 없고 공식 자료라도 이용 조건이 다르다.
- 대안: 조건 미확인 PDF 일괄 수집 / 공공누리 제1유형 텍스트가 명시된 공식 지침 발표·교육자료 우선 수집.
- 선택·이유: 후자를 선택, 출처/기관/게시일/해시/라이선스/원문 위치를 기록하고 이미지·불명확/변경금지 후보는 제외했다.
- 제약·단점: 현재 3건은 2020~2021 게시본, 영양소 섭취기준 전문·최신판·에너지 공식을 대신하지 않는다. 정성적 원칙만 선택하며 수치 처방에는 사용하지 않는다.
- 검증 근거: `data/guidelines/manifest.json`, `chunks.jsonl`, W008. 임베딩·검색 품질은 미검증.
- 재검토 조건: 최신 공식 지침 확보, 이용 조건 변경, 원문 본문 수정·인용 불일치 발견 시.
- 관련: `scripts/collect_guidelines.py`, `scripts/prepare_guideline_chunks.py`, `data/guidelines/README.md`.

## D006 — 식단용 메뉴는 원문 대조한 레시피 자체의 1인분 영양을 우선

- 날짜·상태: 2026-10-21 / 확정(사용자가 레시피 영양 기준 우선 확인 방향을 승인).
- 문제: D005의 이름 후보는 영양 동일성을 보장하지 않으며 일반 음식 매칭만으로 레시피 영양을 확정하기 어렵다.
- 대안: 일반 음식 이름 매칭 / 재료별 영양 추정 / 공식 원문에 확인되는 레시피 자체 영양 사용.
- 선택·이유: 세 번째를 우선한다. 같은 레시피의 원문 1인분 표시·재료·5종 영양값을 대조하고, 확인된 메뉴만 별도 데이터로 보관한다.
- 제약·단점: 현재 6개만 확인, 중량 환산 불가. API 전체를 1인분으로 일반화하지 않으며 제외 재료/개인화 준비는 별도 검증이 필요하다.
- 검증 근거: `data/recipe_basis_audit.json`, 공식 PDF URL·해시·페이지, W006. 영양 실험 정확성·효과는 미검증.
- 재검토 조건: 공식 제공기관의 전체 기준 설명 확보, 원문과 API의 버전 차이·재료/수치 변경 발견 시.
- 관련: `docs/RECIPE_NUTRITION.md`, `scripts/audit_recipe_basis.py`, `data/recipe_serving_menus.json`.
- 이전 결정과 관계: D005의 이름 매칭 우선 작업 순서는 대체됨. 후보/확정 분리 및 제외 조건 우선 원칙(D002·D005)은 유지한다.

## D005 — 이름 후보와 영양 연결 확정을 분리하고 개인화 조건을 우선 검증

- 날짜·상태: 2026-10-21 / 확정(사용자 개인화 의도를 구현하기 위한 LLM의 단계별 구현 선택).
- 문제: 기존 음식과 레시피 표본이 다르고, 이름이 비슷해도 변형 메뉴에 일반 음식 영양값을 붙이면 오해가 생긴다.
- 대안: 이름 유사도로 자동 연결 / 추가 영양 후보 확보 후 검토 단계 분리. 후자를 선택했다.
- 방법·이유: D002를 유지·구체화한다. 원본은 보존하고 후보 연결만 생성한다. 제외 조건을 선호보다 우선하며 미검토 재료·영양과 에너지 모델 미구성을 차단 사유로 남긴다.
- 제약·단점: 현재 확정 연결 0건으로 최종 개인화 추천은 아직 제공할 수 없다. 단순 문자열 기반 후보와 동의어는 오탐·누락 가능성이 있다.
- 검증 근거: `data/matching_report.json`, `tests/test_menu_data.py`, W005. 사용자별 정확도 향상은 미검증.
- 재검토 조건: 레시피별 동일 조리식품 근거·기준량 확보, 공식 계산식 선정, 정답 연결표 평가 완료 시.
- 관련: `docs/MATCHING.md`, `scripts/build_menu_catalog.py`, `scripts/menu_personalization.py`.

날짜는 결정이 대화·코드에서 확인된 날이다. 사용자 요구와 LLM 구현 선택을 구분한다.

## D001 — 수치 계산과 근거 설명 분리

- 날짜·상태: 2026-10-21 / 확정(사용자 기획).
- 문제: LLM이 음식·수치를 생성하거나 근거 없는 건강 설명을 할 가능성.
- 대안: 수치까지 LLM 생성에 맡기는 방식과 코드 계산 후 근거 설명 방식. 전자는 채택하지 않았으며 실제 비교 실험은 없다.
- 선택·이유: Python이 수치/조건/ID를 검증하고 RAG·LLM이 확보 문서로 설명하여 검증 가능하게 한다.
- 제약·단점: 계산 공식·구조화 데이터·문서의 적용 대상 및 단위를 별도로 관리해야 한다.
- 근거·가정: 사용자 원안 `history.md` 6절. 서비스 구현 효과는 미검증.
- 재검토 조건: 계산 기준·대상 사용자가 변경되거나 설명에 계산 근거가 누락될 때.
- 관련: `docs/PROJECT.md` 계산과 RAG 역할. 계산·RAG 코드는 아직 없다.

## D002 — 영양·레시피를 별도 보관하고 불확실 연결을 명시

- 날짜·상태: 2026-10-21 / 확정(사용자 연결 원칙 + LLM 데이터 구현).
- 문제: 같은 이름이라도 재료·조리 상태·기준량이 다르면 잘못된 영양 수치가 붙는다.
- 대안: 이름만으로 즉시 연결 / 별도 ID 유지 후 검토. 이름만으로 연결하지 않는 것은 사용자 요구다.
- 선택·이유: 음식/레시피 ID를 분리하고 `nutrition_food_id=null`, `matching_status=unreviewed`를 저장한다.
- 제약·단점: 검토 전에는 통합 메뉴 추천과 정확한 영양 연동이 제한된다.
- 근거·가정: `scripts/collect_recipes.py`의 `normalize`; W003·W004. 레시피 영양 기준량은 미확인이다.
- 재검토 조건: 재료·조리 상태·기준량이 확인되는 연결 근거를 확보할 때. 과거 불확실 사유도 보존한다.
- 관련: `data/recipes.json`, `data/README.md`.
