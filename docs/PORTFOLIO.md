## P001 — 공개 API의 영양·레시피 데이터 확보

- 문제: 식생활 서비스에 사용할 영양 수치와 재료·조리법의 실제 확보 가능성을 확인해야 했다.
- 내가 맡은 역할(사용자, 대화 확인 범위): 서비스 기획 제시, API 신청, 키를 로컬 환경에 저장, 영양 API 주소 제공. 코드 작성·수집 실행은 이 대화에서 LLM이 수행했다.
- 제약·초기 상태: 데이터·수집 코드 부재, 서로 다른 API 인증 방식, 네트워크 제한. 원래 제시된 소 이동 API는 목적에 맞지 않았다.
- 방법·이유: D001~D003 참조. 원본과 정리본을 분리하여 출처 확인 및 후속 계산을 준비했다.
- 실제 구현: 영양·레시피 수집기 2개, 정규화 JSON·엑셀용 CSV·수집 보고서, 미확인 연결 상태 명시.
- 검증·결과: W002~W004. 각 100건의 고유 ID, 기준량 및 주요 필드 존재를 확인했다. 서로 연결된 메뉴 100개를 확보한 것은 아니다.
- 증거: `scripts/collect_nutrition.py`, `scripts/collect_recipes.py`, `data/raw/`, `data/collection_report.json`, `data/recipe_collection_report.json`.
- 한계·개선: 영양 표본 편중, 레시피 매칭·이용 조건 미확인. 계산·RAG·UI·사용자 효과는 아직 성과로 제시할 수 없다.
- 설명 가능한 배운 점: 서비스 목적에 맞는 API인지 먼저 확인하고, API 항목 수·필드 존재와 실제 메뉴 연결 가능성을 구분해야 한다. 수치 비교 전에 기준량을 확인해야 한다.

## P002 — 작업 인수인계를 위한 문서 구조 설계

- 문제: 긴 단일 기록에 기획·이력·이전 상태가 섞여 맥락을 다시 설명해야 했다.
- 내가 맡은 역할(사용자): 읽기 비용·인수인계·포트폴리오라는 목적과 문서별 작성 기준을 정의했다. 파일 작성은 LLM 수행.
- 제약·초기 상태: `history.md`에 유효한 요구사항과 오래된 상태가 공존; Git 이력 없음.
- 방법·이유: D004. 시작 문서 두 개와 필요 시 읽는 기준/결정/이력/근거 문서를 분리했다.
- 실제 구현: `AGENTS.md` 및 `docs/`의 5개 문서 생성, 이전 기록 보존·참조 경로 제공.
- 검증·결과: W004. 현재 데이터 상태를 로컬 파일로 재확인하고 문서 줄 수·링크를 확인했다. 토큰 절감량·인수인계 시간은 미측정.
- 증거: `AGENTS.md`, `docs/STATE.md`, `docs/DECISIONS.md` D004, `docs/WORKLOG.md` W004.
- 한계·개선: 후속 작업에서 선택적 갱신 규칙을 지켜야 하며 모든 LLM의 자동 로딩을 보장하지 않는다.
- 설명 가능한 배운 점: 최신 상태를 누적 이력에서 분리하고 실측·사용자 의도·미검증을 구분해야 문서가 작업 근거로 쓰인다.
